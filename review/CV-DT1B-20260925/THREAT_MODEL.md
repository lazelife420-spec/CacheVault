# CV-DT1B — Threat Model

**Scope:** Windows Mobile Bridge and Android paired-device transport/enrollment, as observed on 2026-09-25 and proposed in `SECURE_ENROLLMENT_TRANSPORT_DESIGN.md`.

**Trust boundary:** LAN discovery supplies a candidate address only. The intentional QR supplies a one-time enrollment secret and pinned local server trust anchor. Owner approval grants a subset of scopes. After enrollment, Android mTLS proves device-key possession; an expiring session credential carries the currently granted authority. Every request remains subject to Mobile Access enablement and the shared Vault Lock state.

The table describes target controls; they are not implemented or runtime-qualified. Residual risks are explicit.

| Threat / condition | Current exposure | Target control | Residual risk / qualification |
|---|---|---|---|
| Passive LAN observer | HTTP exposes bearer tokens, requests, responses and discovery metadata to local-network observation. | TLS 1.2+ with pinned local CA; mandatory mTLS and no cleartext fallback. | A compromised endpoint, rooted phone, or traffic captured after decryption is outside transport protection. |
| Active MITM / rogue access point | Cleartext bridge allows interception and response substitution; discovery does not authenticate the PC. | Android validates the QR-pinned CA, certificate chain and endpoint identity; server requires a valid client certificate after enrollment. | Trust bootstrap still depends on owner scanning the intended QR and confirming the intended PC/device. Misleading owner UI can defeat consent. |
| Malicious LAN peer | Can discover the advertised service and currently can invoke tokenless pairing while Mobile Access is enabled. | Discovery remains address-only; all normal routes require mTLS, an active device, session, scope, enabled state and unlocked state. Pairing requires the one-time offer and owner approval. | A LAN peer can still scan/DoS the listener. Rate limits and bounded request parsing remain necessary; LAN membership itself is never trust. |
| Copied QR / copied offer secret | Existing QR token is valid for up to five minutes, and endpoint does not require it. | 120-second secret, distinct public offer ID, stored verifier, atomic one-time consumption, owner-visible pending device details and explicit approval. | A copied QR can race the intended phone and cause a pending request or denial of service. Owner must reject an unexpected request; approval binds the public key actually shown. |
| Expired QR | Current offer expiry is five minutes; expiry semantics depend on the process-local offer manager. | Server checks authoritative expiry on every consume; expired offers are invalidated and require explicit regeneration. | Clock skew affects displayed expiry only; server monotonic/UTC policy must be explicit and tested across process restart. |
| Replayed pairing offer | Current consume path is not synchronized; concurrent replay may pass a nominal single-use check. | Atomic state transition `ISSUED -> CONSUMED` under a lock/transaction before creating pending enrollment; replay returns a generic rejection and never issues a second identity. | A successful first-use attacker may win a race; owner approval and displayed key fingerprint are the final enrollment gate. |
| Stolen legacy bearer token | Current long-lived bearer is replayable over HTTP and stored as a verifier in settings; Android persists it in encrypted preferences. | Protocol 2 rejects all protocol-1 bearers. New session token is high entropy, short lived, hash-only server-side, bound to matching mTLS device certificate and granted scopes. | Theft of an unlocked/rooted phone may permit use until revocation/expiry. TLS client key protects against token-only replay but cannot protect a fully compromised app/device. |
| Stolen new session credential | Token may be extracted from app memory/storage or logs. | AndroidKeyStore AES-GCM wraps the token at rest; never log tokens; server requires matching client cert and checks expiry/revocation/scope per request. Rotate on renewal and revoke all tokens on device revoke. | While attacker also controls the matching private key or live device session, the credential may be usable. Reduce lifetime and close active connections on revoke. |
| Revoked device | A previously paired client may retain bearer material and an established connection. | Mark device revoked; invalidate all session credentials; deny at TLS/request authorization; close registered active TLS sessions; cancel pending enrollment; record safe audit event. | Bytes already delivered or copied cannot be recalled. In-flight response races require checks before sending body chunks where practical. |
| Lost phone | Existing bearer remains usable until removed/revoked; encrypted preferences alone do not give server-side expiry. | Owner revokes device from Windows; all sessions invalidated and active connections closed. AndroidKeyStore private key is non-exportable where platform guarantees it. | A powered-on, unlocked phone can be used before revocation. Recovery requires owner-accessible device management and a tested revocation path. |
| App reinstall / app data clear | Pairing material may be lost or restored inconsistently; device ID can be caller-supplied. | Keystore key or wrapped-session loss invalidates local credentials; reinstall is a new enrollment with a fresh server-assigned device ID. Backup remains disabled; no automatic identity restoration. | Old server certificate entry remains until owner revokes it or retention cleanup removes stale devices. Reinstall must not silently clone identity. |
| IP address change | Discovery/resolution uses a current IPv4 address; endpoint address can change. | mDNS/manual address only locates the host. TLS CA and certificate identity, not IP or service name, authorizes the host. Reissue leaf with current SANs under the same CA or use a stable authenticated host name. | A direct IP certificate needs matching IP SANs; changing network addresses may require safe leaf renewal. Never disable name checks as a workaround. |
| Server certificate or CA/key rotation | No authenticated TLS identity or rotation protocol exists today. | Leaf renewal under the same pinned CA is transparent if SANs remain valid. CA rotation uses overlap authenticated by the existing trust anchor or explicit owner-led re-pair; retain current/next pins during transition. | Loss of Windows DPAPI-protected CA key requires re-pairing. A malicious or corrupted trust-store update could lock out clients; test power-loss and recovery. |
| Android device-key rotation / invalidation | No client public-key identity exists. | New certificate must be bound to the new AndroidKeyStore key through authenticated old identity or fresh QR enrollment; revoke old serial and sessions. | Hardware reset, lock-screen change, OS/vendor invalidation, or key loss forces re-enrollment. Hardware backing is device-dependent. |
| Downgraded legacy client / protocol downgrade | Protocol 1 and HTTP remain accepted; client compatibility version is 1. | Protocol 2 is the sole accepted bridge protocol when enabled; require TLS/mTLS and reject protocol-1/cleartext requests rather than fallback. Capability negotiation must be authenticated and monotonic. | Old mobile builds will stop pairing/accessing the bridge and need an update. Rollback must keep Mobile Access disabled rather than reopen v1. |
| Lock transition during request | Existing lock gate denies requests checked after lock, but content work already admitted may race a transition. | Check the canonical Vault Lock authority before dispatch and again before protected response delivery; cancel active work/connections where safe. Pairing also returns `423 vault_locked`. | Cannot erase data already sent. Define exact chunk/cancellation behavior and test lock during large asset and inbox operations. |
| Mobile Access disabled during request | Disabling the feature may race with an already admitted request or pairing. | Check enabled state before dispatch and before response/side effect; invalidate sessions/offers and close listener/connections on disable. Pairing is forbidden while disabled. | An operation already committed before disable cannot be rolled back automatically. Define transaction boundary and audit outcome. |
| Malicious owner-approved phone / scope abuse | Current bearer can access broad routes; content summaries include sensitive metadata. | Least-privilege per-device scopes; default summary excludes Safe and sensitive items; detail and receive are separate grants; no export/delete/admin scopes in tranche 1. | An approved device can still misuse the scopes the owner grants or take a permitted screenshot/copy. Scope labels and grant UI must be understandable. |
| Receipt/log disclosure | Receipts contain route/action/result/device metadata, clip ID and remote IP. | Preserve minimal safe audit records; never store offer secrets, private keys, raw bearer/session tokens, request bodies or authorization headers. | Metadata can reveal usage patterns and local network addresses; retention/access policy needs product review. |
| Denial of service / malformed input | LAN listener accepts network requests and thread-per-request handling can consume resources. | Bound headers/body sizes and concurrency; reject malformed/oversized payloads early; rate-limit enrollment and authentication failures without leaking secrets. | Local network peers can still consume bandwidth/CPU. Availability is not guaranteed against a host-level adversary. |

## Security invariants for implementation review

1. Discovery data and device-supplied names/IDs are untrusted; only the server assigns device IDs.
2. Pairing requires the explicit QR offer and owner confirmation; no mDNS or “Mobile Access enabled” shortcut enrolls a device.
3. The initial enrollment request is the sole mTLS exception: pinned server TLS plus the live offer is required before a client certificate exists. It creates only a pending request. A device becomes trusted only after owner approval and certificate issuance.
4. Every protected API request requires protocol 2, TLS/mTLS, active device, valid certificate, unexpired session credential, route scope, Mobile Access enabled, and Vault Lock access. The lock gate is independent and never inferred from successful authentication.
5. Revocation, lock, and disable transitions prevent new protected response bytes where practical; no claim is made that bytes already delivered can be recalled.
6. Neither enrollment, TLS, nor device trust encrypts Windows database/image data at rest. At-rest encryption remains a separate design and implementation lane.
